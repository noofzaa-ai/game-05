## M1-1: owned data

`Item`, `Inventory`, `Loadout`, `Profile`, `Run`, `Journey` expose `to_dict()` and
`static from_dict(...)`. Every object has `v: 1`. Unsupported versions return
null; the calling storage/session layer must reject them. These loaders consume
trusted saved records, not arbitrary requests from a player. Required fields
must exist; schema validation/migrations at the storage boundary belong to M3.

Supply current rule books on load: item rules, camp data and, for Journey,
journey/loot definitions and weapon IDs. No stat totals, catalog models, material
stack definitions or combat rules are persisted. Inventory capacity is retained
because debug/test kits can increase it beyond camp facilities. A Run includes
its Profile; Journey includes its Run. A session must keep a single ownership
graph (restored `journey.run.profile`, not an unrelated separately loaded Profile).
`Run.from_dict` optionally accepts an already restored Profile for this purpose.

GDScript JSON's decimal conversion changes some last bits of floats. V1 therefore
stores durability, max durability, rolled substat quality, HP fraction and gauge
as **16-character little-endian IEEE754 hex strings** (`StateCodec.float_text`).
Gold and the journey seed are decimal strings, preserving integers above 2^53.
Other bounded integer counts remain JSON numbers and are cast back explicitly.
Round trips work through ordinary `JSON.stringify` / `JSON.parse_string` without
requiring special JSON options. Do not interpret the float strings as decimals.

Tests cover all 15 worn positions, destroyed/enhanced/damaged gear, paired slots,
materials, large gold, appearance/name/facilities, consumed rests, death, route,
rewards with Item objects, independent ownership and continued Journey progress.

## M1-2: command boundary

`Commands.apply(context, request, rng)` returns `{ok, changes, result}` or
`{ok: false, error}`. `context` is constructed by the future trusted Session/server:

```
{profile, rules, camp, location: "camp"|"rest"|"stage", run?, cosmetics?}
```

A request may not supply context, rules, prices or a replacement item payload.
Unknown fields, wrong types and fractional indices/counts are rejected. JSON
integral floats are accepted as integers within signed 32-bit range.

| type | request fields |
|---|---|
| equip | item (instance ID), source (stash/bag), index (optional, default 0) |
| unequip | slot, destination (stash/bag), index (optional) |
| discard | item, source |
| discard_material | material, count, source |
| repair | item |
| repair_all | none |
| upgrade_camp | none |
| upgrade_facility | facility |
| appearance | part, choice |
| set_name | name |
| enhance | item, protect (optional) |
| upgrade_tier | item |

All item commands verify ownership by ID, reject ambiguous/empty IDs, and check
container membership. Stash operations require camp; changing equipped gear in
combat is rejected; bag access requires a live Run. Existing Camp, Profile, Run,
Repair and CosmeticOptions rules decide capacity, equipment slots, prices,
facilities, naming and choices. Failed commands leave owned data and RNG unchanged.
`set_name` checks syntax only: uniqueness requires M3 server storage.

**Boss decision 2026-10-17:** enhancement and tier-up have no economic price or
protection-consumption configuration in the existing data. Both commands return
`not_configured`, even when the item exists. They cannot grant free upgrades.
A later feature must add server-owned prices/protection rules and tests before
enabling them. This is an explicit exception to M1-2's original success cases.

UI continues to call the old paths until M1-6. No client files were changed here.
The trusted Session must determine camp/rest/combat availability from actual
simulation state, never from the request's claims.

## M1-3: full checkpoints

`GameSim.snapshot()` keeps all previous drawing keys and adds `v: 1` and
`checkpoint`. The latter is a lossless JSON-compatible tagged array generated by
`StateCodec`; it includes:

- every stored body, fighter and input field (computed `facing` is excluded in
  favour of `direction`), including hit IDs, cooldowns, effects and stamina;
- all AI configuration and private navigation/attack/flee/cooldown state;
- world bounds and collision solids;
- `_ranged` including next ID, active projectiles/areas and hit lists;
- tick, events, queued waves, released counter and clear-report flags;
- RNG seed and state as exact 64-bit integers;
- attached Run/Profile/loadout/bag ownership.

`sim.restore(snapshot, camp_data)` uses the same combat/rules supplied to the
new sim. Set `sim.item_rules` and `sim.loot_data` before restoring a snapshot
with attached Runs. Missing dependencies/version mismatch return false before
mutating the sim. AI references bind to the restored world's object. Arrays retain
their element types; dictionaries retain key types **and insertion order**, since
tie-breaking currently uses insertion order. Checkpoints are trusted records,
not a safe deserializer for untrusted network payloads. M4 must validate frame
lengths, versions and rule/build compatibility before accepting server snapshots.

Tests compare immediate complete state and 300 + restore + 300 against an
uninterrupted 600 ticks for normal/boss maps; another test restores with live
projectiles, warning areas and pending boss waves, then compares each next tick.
Captured snapshots remain independent of later mutations.

### Determinism defect fixed

Loot previously used a process-global `_next_id`. Two independent rooms or a
restored sim could produce different IDs despite identical seed/inputs. Instance
IDs now use the supplied stream's **seed + state** at the item roll. This consumes
no extra random draws and leaves drop probabilities, rolls and combat unchanged.
Future server sessions must allocate distinct seeds/stream namespaces per run;
reusing the exact same stream while retaining items would reproduce their IDs.

The existing movement-only determinism test now explicitly copies the initial
RNG seed/state between sims: complete snapshots include RNG even when unused.
No gameplay default RNG behaviour was changed.

## M1-5: input wire layout v1

Five bytes, no objects, allocation-size ambiguity or platform endianness dependency:

| byte | meaning |
|---|---|
| 0 | jump/light/heavy/run/guard/dodge/special/ultimate, bits 0..7 |
| 1, 2 | signed move x/y, -127..127 |
| 3, 4 | signed aim x/y, -127..127 |

Nonfinite axes become zero. If either component exceeds magnitude 1, both
components scale by the largest magnitude, preserving world-space aim direction.
Axes then round to nearest integer at 127 scale. Decode rejects lengths other than 5 and reserved
-128 axes. Eight held/pressed flags round-trip; higher-level tick delivery and
edge semantics remain the caller's responsibility. M4 will add framing/version,
tick IDs, replay history and bounds outside this payload.

**Not wired into live offline play yet:** M1-6 LocalSession must encode/decode
before each simulation input, just as RemoteSession/server must. Introducing
that integration here would change existing offline movement/aim and violate the
M1-1..5 scope. Existing bot tests explicitly exercise the future codec boundary.

### Authority and read contract

`client/session/local_session.gd` owns the stage GameSim, Run, Journey and command
context. GameState keeps one Session across the creator, hub management screens,
stages and Journey route screen. It recreates it if the profile/rule references
change (isolated tests and fresh games). Profile/test-kit initialization is owned
by Session; the debug provisioning implementation lives in `logic/test_kit.gd`.
The old client test-kit module is a compatibility facade for screenshot tools.

The stage's `_sim` field is replaced by `_session`. Stage presentation, projectiles,
audio, HUD, cameras and effect handlers read through that contract:

| API | purpose |
|---|---|
| `begin_stage(map, combat, journey, player, first_enemy, rng)` | establish authoritative actors and return initial view metadata |
| `step(input)` / `set_input(id, input)` + `tick()` | accept input, quantize by encode/decode, advance exactly one fixed tick |
| `bodies`, `fighters`, `events`, `projectiles`, `areas`, `combat`, `tick_count` | borrowed read views for the renderer/audio |
| `snapshot()` | full M1-3 checkpoint plus current Journey owned data, on demand (not rebuilt every render frame) |
| `living_enemy_count()` | authoritative display query |
| `command(request)` | validated Commands boundary, including live gear-stat/style refresh |
| `open_rest(point)` / `close_menu()` | validate the actual point/proximity and pause/resume ticks |
| `use_rest()` | use only the currently authorized point, respecting GameSim's once-per-trip rule |
| `open_route_camp(point)` | camp menu from the existing route-list fallback, validated against Journey state |
| `capture_gauge()` | preserve the live gauge when taking a portal |
| `enter_camp()` | release stage sim/run/Journey references after returning home |

Read views are borrowed objects for compatibility with existing renderers, not
immutable copies. UI must not mutate them. The Session implementation alone
advances the sim and applies lifecycle consequences (clear/death, HP/gauge carry).
A future RemoteSession must provide equivalent view shapes and command results.
This is a local authority, not a network transport or a secure client sandbox.

The hub's existing movement-only walking controller is unchanged. Its camp
inventory/creator use the shared Session; online camp avatars remain M5 work.

### UI changes and permissions

Camp, gear, look, creator, Journey route and stage reward/banking handlers now

Detached sessions are for local tools/fixtures, never remote authorization.

Commands now also cover random appearance, Journey choice/leave/treasure/abandon/
retreat/finish, marking the already-healed camp rest, and bag banking. Core command
responses contain JSON-compatible owned records (including treasure Item data);

The request never chooses its own location/context. Physical rest access is checked

Opening a rest window freezes simulation ticks, closing resumes them. Gear commands

Existing free-stage early-Esc banking is preserved; a Journey cannot use that path.

rewards. No economy, enemy strength or skill timings were changed.

## M2 — local party simulation (2026-10-17)

Implemented on `codex/m2-local-coop`, stacked on M1-6. This is local authority;
there is still no network transport, lobby, account storage or dedicated room process.

- `logic/coop_journey.gd` extends the solo Journey with separate Runs/profiles,
  HP fractions, gauges, downed deadlines and rewards. Route choice stays shared.
  Camp heals surviving participants once; eliminated participants stay out until
  the next Journey. Checkpoints include every participant and reward summary.
- Explicit `GameSim.enable_coop()` enables 2–4 participants. Solo remains opt-out.
  Monster HP uses data multipliers **1 / 1.6 / 2.2 / 2.8**, including later boss
  waves; ATK is not multiplied by party size. Safe spawns respect world bounds,
  solids and body extents; an impossible setup returns an error before stage play.
  Optional map `player_spawns` supplies preferred positions, with safe fallback.
- Fatal damage/DoT becomes `DOWNED` before the economy can discard the bag.
  Standing idle and grounded near an ally accumulates revive progress; moving,
  attacking, leaving range or switching helpers resets it. Each helper revives
  one ally at a time. Bleedout eliminates the participant and loses their bag.
  All incapacitated/eliminated means `team_wiped` once and every bag is lost;
  worn equipment/stash remain, with normal death wear. A simultaneous final kill
  and full team wipe is a loss for the party.
- Provisional `combat.json` tuning: **600 ticks / 10s** bleedout, **120 ticks / 2s**
  idle revive, **2m** range, **30% HP**, **60 ticks / 1s** revive invulnerability.
  These values are test defaults, not a combat-design acceptance decision.
- Every enemy death independently rolls loot for each non-eliminated participant,
  including downed allies; `loot.player` identifies the recipient. Duplicate death
  processing cannot pay twice. Treasure/challenge rewards are also per player.
- Session remains the mutation boundary. The local leader's death does not end a
  party with survivors. Completion/retreat banks all participants' bags. A dead
  leader may still issue shared route commands, but cannot manage dead-run gear.

## M4 protocol v1 specification (2026-10-17, before transport implementation)

Status: the specification below preceded M4-2..6 implementation. The implemented codec contract and test status follow it; native/local technical checks do not certify physical-device feel or live k3s deployment.

- All integers on game wire are unsigned little-endian unless stated. WebSocket binary frames only after admission; reject unknown version/type, invalid length and out-of-range values before allocating. JSON private control is not the gameplay wire.
- Common header: magic0x585a(u16), version1(u8), type(u8), sequence(u32), payload_bytes(u32). Hard frame ceiling64KiB; handshake/checkpoint chunks bounded separately to256KiB assembled with timeout. Sequence is connection-scoped and strictly increasing; reconnect starts a new generation. No Object/Variant deserialization from peers.
- INPUT type1: state_ack(u32), event_ack(u32), epoch(u32), target_tick(u32), count(u8,1..4), count five-byte SimInput records newest first (tick, tick-1..tick-3). Slot/user ID is bound by admission and is never read from the packet. Ignore played/duplicate ticks; reject replacements of queued input, invalid axes(-128), future lead>24 ticks and oversized batches. Missing/disconnected inputs are neutral; one-shot buttons are never repeated automatically.
- STATE type2 at20Hz: server_tick(u32), acknowledged_played_input_tick(u32), baseline_sequence(u32;0=full), entity_count(u16), bounded typed entity records. Fields cover position/velocity/grounded/facing/HP/energy/gauge/state/move/frame/effects; no client-supplied damage or ownership. Full state on admission/reconnect; deltas reference an acknowledged baseline, otherwise request full. Exact entity-field codec and quantization must be implemented/tested before shipping STATE; no generic JSON snapshot fallback.
- EVENT type3: server_tick(u32), event_sequence(u32), bounded typed combat/loot/down/revive records. Event IDs deduplicate replay. Private loot is filtered by recipient; inventory/journey/RNG secrets are not broadcast to other players.
- CONTROL type4: bounded enums for readiness, permitted route choice, rest/menu and full-baseline request. Server validates actor/membership/state/proximity; client cannot pause a shared room, grant rewards or change its location.
- PING/PONG types5/6: monotonic nonce and server tick for clock alignment. Debug delay/loss/jitter is outside the authority and must not alter server rules.
- Admission: Nakama authenticates device/session, checks membership and chooses a configured worker. One-use short-lived room ticket binds user, room, slot and generation. Room verifies/redeems with Nakama over private authenticated service calls before attaching a WebSocket. No signing/runtime/DB key goes to clients. Profile CAS/active-room fencing must precede trusted journey settlement.
- Prediction: local player keeps input history, restores last acknowledged authoritative prediction state and replays remaining wire-quantized inputs. Remote actors interpolate ~100ms behind. Presentation/audio event dedupe is separate. All gameplay ownership remains server-side.
- Reconnect:30s reservation; old connection generation loses authority immediately; actor receives neutral inputs. New verified connection gets full state. Room/process crash does not grant speculative rewards. Offline mode remains an explicit separate local profile.
- Server clock:60Hz monotonic fixed ticks, at most5 catch-up steps/frame; sustained backlog above250ms closes the room with overload instead of changing dt. No client request advances time. Empty rooms retire after30s; inactive route/terminal rooms have a finite TTL. Limits are staging defaults, not throughput certification.

M4 acceptance remains two actual clients completing a Journey at150ms/2% loss,<30KiB/s per person, reconnect and human QA. The spec does not bypass M2 balance, physical phone or backup acceptance gates.

### M4 implemented wire codec contract (before M4-3 code)

Shared `logic/net_wire.gd` uses the12-byte header above and a bounded explicit TLV codec, never Godot Variant/Object deserialization. Tags:0 nil,1 false,2 true,3 signed int64 LE,4 finite float64 LE,5 UTF-8 string(u16 byte length<=8192),6 array(u16 count<=1024),7 dictionary(u16 count<=512, keys int/string only),8 Vector2(two f32),9 Vector3(three f32),10 Vector2i(two i32),11 signed i16,12 unsigned u32. Depth<=12, decoded value budget<=8192, frame<=65536 bytes. Unknown tags, duplicate dictionary keys, invalid UTF-8, nonfinite floats, overlong/deep/truncated/trailing data fail before applying state.

INPUT body is fixed: last acknowledged state-sequence(u32), last consumed event-sequence(u32), stage-epoch(u32), newest target room-tick(u32), count(u8),1..4 five-byte records newest first. Room ticks stay monotonic across stage changes. Peers are rate/queue bounded and stale tick recovery never repeats one-shot buttons.

STATE TLV dictionary contains base-sequence,tick,played-input-ack,stage epoch,entity patches/removals and optional changed meta/projectiles/areas. Entity patches map integer IDs to body/fighter fields by an explicit shared field table; full includes every field, delta only changed indices. Acknowledged baselines retain at most32 states per peer; missing baseline forces full. Only public combat fields, own Run/profile and other players' visible loadouts/appearance are included; no AI decisions/RNG/seeds/other stash or bag. EVENTS are typed bounded TLV records with sequence/tick and recipient filtering; send recent unacknowledged entries and deduplicate at client. CONTROL requests carry bounded command schema and request sequence; replay journal avoids duplicate mutations. Ping/Pong aligns room tick/RTT.

Admission alone uses one bounded JSON frame `{v:1,room,ticket}`. Nakama's authenticated public RPCs create/join a private invite-code room and issue30s one-use tickets. A private RPC verifies server secret/runtime HTTP key, redeems ticket CAS and returns immutable slot/profile/fence. First connection generation is replaced on rejoin;30s disconnected slots use neutral input, then are eliminated. Room lease heartbeat fences profile commands and settlement; expired started leases recover through original Godot death/wear rules. Finished results persist once for all owners in one fenced CAS transaction.

### M4 lifecycle, chunks and debug controls

- The actual STATE/EVENT/CONTROL/PING payloads use the bounded TLV dictionary schema above, not the earlier conceptual fixed-record notation. `BODY_FIELDS`/`FIGHTER_FIELDS` in `logic/net_wire.gd` are the authoritative ordered entity tables. Positions/vectors use f32; other finite numeric fields use f64 or compact integers. No generic Godot Variant decoder is used.
- Oversized STATE starts with byte127 (not a TLV tag), then transfer sequence(u32), fragment index(u16), fragment count(u16), total bytes(u32), raw piece. Final baseline sequence=transfer+count-1. Max256KiB,8 pieces,4 simultaneous assemblies,5s timeout; every frame remains<=64KiB. The large-state TLV value budget is32768; ordinary frames8192.
- Command bodies `{id,epoch,request}` use increasing positive IDs, a64-result replay journal and per-slot watermark. A missing/wrong epoch cannot operate on a new stage. Client pending commands<=32 and retry the same ID/epoch; packets cannot grant loot or change authoritative profiles. Route selection is leader-only; camp equipment is owner-bound.
- Physical map ID survives Journey clearing its current route node. This permits route/terminal snapshots while retaining the visible arena. Epoch increments when a new playable map is loaded, not merely when an actor moves.
- Nakama public RPCs: `zorx_room_create_v1`, `zorx_room_join_v1`, `zorx_room_cancel_v1`, `zorx_room_resume_v1`. Private `zorx_room_backend_v1` requires runtime HTTP key, shared worker secret, configured worker ID and a process nonce. First redeem CAS binds the process. A restart fails closed, never creates a fresh run from the old profile lock.
- Server-derived profile locks renew10s/expire60s; worker stops45s without renewal. Finish commits all owners atomically under room+profile fences. Retrying a closed result is idempotent. An expired started lock is recovered by original Godot death/wear once before unlock; no speculative bag survives a crash.
- `--net-sim=75,10,0.02` enables75ms one-way application delay,10ms jitter and2% loss on each direction. Queue<=512 packets/direction; normal play defaults to no impairment. `--net-debug`/F2 shows RTT, prediction lead and correction count. `--net-account=qa1` isolates native debug account caches. `tools/netcode/play_clients.py` opens1–4 independent windows.
- The current staging allocator selects the single configured `staging-0` worker. Do not scale replicas behind the same endpoint without a room-aware allocator/route. Each process admits at most8 rooms; throughput/load acceptance is not inferred from that bound. A room crash loses the run safely rather than restoring an unimplemented checkpoint.


## M5 party protocol extension (2026-10-17, before implementation)

- Create optionally adds `camp:true`; legacy M4 create remains an immediate Journey at full capacity. Camp-mode capacity is a maximum, not required party size. First admitted member starts a safe shared camp simulation. Later authenticated invitees join that camp; no late Journey joins except reconnecting members.
- Nakama room membership/leases remain the admission source. A camp room never marks its run started until the leader requests departure and every admitted member is connected/ready, with no pending admission. The private start CAS compares worker roster slots with the Nakama membership set. Ready is reset on roster change/disconnect. Camp commands keep server-owned inventory; camp leave persists that owner before membership removal. Empty/failed camps unlock without death penalties.
- Binary CONTROL additions: `{type:"party_ready",ready:bool}`, `{type:"party_depart"}`, `{type:"party_leave"}`, `{type:"party_ping",kind:"here"|"danger"|"help"|"yes"}`. Actor always comes from the ticket binding; epoch/request receipts remain in force. Only leader can depart, every connected member must be ready, and pings are server-positioned/rate-limited. No free chat or client camera/HP/position overrides.
- Public party metadata contains leader slot, capacity, lobby/departed phase, member slot/name/ready/connected, never peer stash. Boss intro is server-authored metadata with epoch/start tick/boss ID and bounded duration. It changes presentation only; owner ultimate cameras remain private to their caster.
- Authenticated `zorx_social_v1` wraps actual Nakama friend requests/list/accept/remove and persistent party-invite notifications. Character-name lookup resolves private authoritative reservations server-side; actor comes from session. Only accepted friends can receive an invite, and sender must own a valid camp invitation. Client lists/acknowledges only its own invite notifications. Links carry room+invite only, never session/admission tickets; consume hash fragment locally and clear it after reading.
- UI follows the existing Night Brass tokens and landscape touch sizing. Friend sounds have a smaller gain than the local actor. Mobile revive holds neutral input inside the existing server-validated proximity/idle rules; it cannot revive remotely. Disconnect/leave/full/maintenance messages use page TEXT maps.
- Technical acceptance uses isolated owned test accounts and four real RemoteSessions, including impaired transport/reconnect/roster changes and a complete Journey. Physical two-phone/two-PC play and subjective feel remain separately reported; no public-user messages, registry pushes or remote apply are part of this development run.

### M6 operations contract
Private POST `/metrics` (`{v:1}`) reports bounded rolling p95/max simulation tick, rooms, players, bytes, memory, backlog and bounded crash/close reasons. Same private bearer authentication as room control; never expose control port to ingress. POST `/maintenance` switches worker admissions; Nakama private `zorx_maintenance_admin_v1` switches global new rooms/members without stopping existing rooms or reconnects. Public authenticated `zorx_online_status_v1` returns only maintenance boolean. `tools/backend/room_ops.py` operates both switches and writes JSONL diagnostics without secrets.

M6 pool allocation uses one CAS lease record per process (maximum8 live rooms, expiry60s) alongside the atomic room/profile reservation. Tickets store that process's distinct WSS URL; backend worker/process fencing still applies. Heartbeats renew allocation/profile/room in one transaction. The pool renderer emits independent one-replica Services and exact `/room/room-N` paths; changing a Deployment to5 replicas behind one Service is unsupported. Capacity/live-device acceptance remains an operator gate.

M6 serialization tuning preserves the existing bytes: authority snapshots materialize shared entities/profiles once per tick and invalidate on commands/presence/finalization; returned snapshots still deep-copy per caller. Public Run serialization skips constructing a Profile only to erase it. Entity deltas may use a bounded per-room cache with frozen exact source comparisons (same-tick distinct baselines are checked); entity TLV bytes are reused only at top-level depth1 and debit the original codec node/size budget. Private meta remains recipient-specific. Tests compare cached/uncached bytes, budget rejection, baseline collisions and snapshot ownership/filtering.
